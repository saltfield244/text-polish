# TextPolish のレビュー

このツールは、**利用者が選択した文章を外部のLLMへ送り、結果を元のウィンドウへ貼り付けて
原文を置き換える**。確認画面を出さない経路(即実行)があり、取り消しは貼り付け先の Ctrl+Z 頼み。
つまり壊れたときに失うのは「アプリの状態」ではなく**利用者が書いた文章そのもの**で、
しかも失ったことに気づきにくい。

ここまでに見つかった不具合は、種類は違っても原因はほぼ4つに集約される。レビューでは
この4点を軸に見ると当たりやすい。コンパイルが通るか・命名が綺麗かは本題ではない。

1. **利用者の文章が、想定していない場所へ流れていないか**
2. **原文や利用者のデータを、黙って失う経路ができていないか**
3. **外から来た値(LLMの応答・Win32の戻り値・OSの共有資源)を信じていないか**
4. **「実装した」で止まっていないか(回帰テストと実機手順の裏打ちがあるか)**

## 進め方

変更の差分（`git diff` / `git diff --staged` / 指定されたコミット）を読み、触っている領域を
特定してから、下の該当節だけを順に当てる。関係ない節は飛ばしていい。
差分だけでは判断できないときは、呼び出し元まで辿る。このアプリは
`App.xaml.cs` と `PaletteWindow.xaml.cs` が2つの経路（即実行とパレット）の入口で、
同じ Core の部品を違う順序で使うため、**片方の経路だけ直して他方が漏れる**のがよくある形。

指摘は「場所（`file:line`）／何が起きるか／どの条件で起きるか／どう直すか」の順で書く。
再現条件を書けないものは、確認した事実と推測を分けて、推測だと明示する。
何も見つからなければ「この観点では問題なし」と書く。無理に数を揃えない。

## 1. 文章とキーの流れ先

利用者の文章が通る先はこれだけある。**新しい出力先が増えた差分は、それだけで要注意**。

| 流れ先 | 見るところ |
|---|---|
| LLMへのリクエスト | `LlmPromptBuilder` / `Polish.SendSurroundingContext`(既定オフ。選択範囲外の文章は送らない) |
| ログファイル | `IAppLogger` の呼び出し全部。`%AppData%\TextPolish\logs\` に平文で残り、不具合報告に添付されうる |
| クリップボード | 書き戻し中止時の退避(`App.xaml.cs` の退避ログ)、`SelectionCapture` |
| トレイ通知 | 通知の文面に原文・応答本文を入れていないか |
| `appsettings.json` | 履歴・設定に文章が混ざっていないか(自由指示の履歴は別ファイル) |
| 例外メッセージ | 利用者に見せる文面と、ログに書く文面の両方 |

ログに書いてよいのは**形が決まっているもの**だけ。文字数、HTTPステータス、終了理由、
エラー種別、列挙型の結果。LLMの応答本文・原文・整形結果は入れない
(`LlmErrorSummary` / `LogSanitizer` が既にあるので、新しい失敗経路を足すならそれを通す)。
APIキーは `?key=` / `Bearer` / `sk-` / `AIza` の形で混入する。`FileLogger` が最後に落とすが、
依存していいのは形が決まっている秘密だけで、**文章は機械的に落とせない**ことを忘れない。

`_logger.Error(message, ex)` の第2引数は `Exception.ToString()` を丸ごと書く。サーバーの
応答本文をメッセージに含む例外（JSONの解析失敗など）では、そこから本文が漏れる。

ログ自体の作りも見る。1件が1行に収まるか（改行を含む文面は行を分断し、後から読めなくなる）、
常駐アプリとして日付やサイズで切り替わるか、書き込み失敗を黙って捨てていないか。
利用者の中止やタイムアウトは異常ではないので、ERROR で残すと本物の障害が埋もれる。

## 2. 原文を失う経路

- **LLMの応答を採用する条件**。`finish_reason` / `finishReason` が `length` / `MAX_TOKENS` なら
  本文があっても採用しない(`LlmResponseReader`)。原文へのフォールバックもしない。
  黙って未整形のまま置き換えると「整形したのに変わっていない」が起きる。
  終了理由が無いこと自体は異常としない(返さないサーバーがある)。
- **クリップボードの退避・復元**。退避するのは全形式(画像・ファイル一覧・書式付きテキスト)。
  テキストだけ戻す実装に戻っていないか。復元は**遅延**して行い、待機中に利用者が
  コピーした内容を上書きしない。アプリ終了時は待たずに復元する。
- **貼り付け先の照合**。送出の瞬間に前面のウィンドウへ貼り付く。取得元と違えば
  **Ctrl+V を送らずに中止**し、整形結果を失わないようクリップボードへ退避する。
  照合を省略する分岐（取得元不明）を増やしていないか。
- **パレットの結果状態**。書き戻せるのは「今回の整形が成功した結果」だけ
  (`PolishResultState`)。再整形の失敗・中止・タイムアウトの後に前回の結果を適用できると、
  利用者は英訳したつもりで整形結果を貼ることになる。
- 書き戻しは不可逆なので、**迷ったら中止して通知する**が正解。黙って続行は最悪。

## 3. 外から来た値

- **LLMの応答**。JSONの形は保証されない。`choices` / `candidates` が無い、`parts` が複数、
  `parts[0]` が `"thought": true` の思考テキスト、`content` が空、`code` が文字列でなく数値。
  落ちるのではなく「採用しない理由」に変換して同じ経路で利用者に伝える。
  サーバーが決める識別子をログや分岐にそのまま使うなら、長さと文字種を検査する。
- **Win32の戻り値**。`SendInput` は `cbSize` が合わないと**何も送らず0を返す**。
  `SetForegroundWindow` は失敗する。戻り値を見ずに次へ進んでいないか。
  ウィンドウが閉じられている場合の分岐があるか。
- **クリップボードはOSの共有資源**。クリップボード履歴や他プロセスと競合し、
  WinForms の `Clipboard` は短い間隔の読み書きで `ExternalException` を投げたり空を返す。
  検証対象側ではリトライで吸収する（`ClipboardSnapshot`）。テストを緩めて通すのは逆。
- **非同期とスレッド**。`Clipboard` はSTAスレッドからしか呼べない(スレッドプール不可)。
  `WH_KEYBOARD_LL` のコールバックは同期的に呼ばれるのでそこから `async void` を呼ばない。
  ホットキーの連打と2経路の同時実行は `OperationGate` で排他し、**取得を始める前から**保持し、
  例外・キャンセル・選択なしのどの経路でも解放する。

## 4. 検証の裏打ち

- 判定ロジックは純粋な関数に切り出して、`src/TextPolish.Tests` で組み合わせを固定する。
  Win32 や HTTP を含む部分はスタブ(`HttpMessageHandler` の差し替え)で回せる形にする。
- テストは**外部NuGetゼロ**。xUnit等は入れず、`Program.cs` のランナーに `All()` を登録する。
  デスクトップを使うテストは `--no-clipboard` で除外できる側に置く(CIはこれで走る)。
- 新しいテストが**本当に失敗を検出するか**を一度確かめる。直した箇所を一時的に戻して
  FAIL することを見てから戻す。通っていることと、見ていることは別。
- 自動化できない部分（フォーカス移動・キー送出・実際のLLM応答・ログの中身）は
  `src/TextPolish.Tests/README.md` の実機確認手順（A〜H）に項目を足す。
  「コードが入っていることは、動くことの証明ではない」(`RELEASE-チェックリスト.md`)。

## 5. プロジェクトの約束

- 外部NuGetパッケージはゼロ。これを崩す提案は、代替案とあわせて明示的に相談する。
- コメント・ログ・コミットメッセージ・ドキュメントは日本語。改行は CRLF。
- 設計判断を変えたら `IMPLEMENTATION-NOTES.md` に**なぜそうしたか**を残す。
  利用者に見える変更は `CHANGELOG.md` の v1.0.2 節へ。テストの観点は
  `src/TextPolish.Tests/README.md` の表へ。v1.0.2 のリリース準備資料は作り直さない。
- 既に実装されている動作（終了理由の判定、APIキーの暗号化、排他、照合）は、
  指摘の対象でない限り触らない。レビューの範囲を勝手に広げない。

## 外部の指摘を受け取ったとき

Codex や他のレビューの指摘は、**正しいことが多いが、確認しないまま直すと範囲が膨らむ**。

1. 指摘されたファイルと行を実際に開き、現在の `main` でまだそうなっているかを確かめる。
   既に直っている・前提が違う場合もある。
2. 指摘の中の「確認できた事実」と「可能性の話」を分ける。
   例: ログに本文を書いているのはコードで確認できる事実。実際に漏えいした事例があるかは別。
3. 同じ原因が**他のプロバイダ・他の経路にも**ないかを横に広げて見る
   (3つのFormatter、即実行とパレット、3つの設定プロバイダは対称に直す)。
4. 指摘が明示した範囲に修正を収める。関係ない改善を混ぜない。
5. 直したら、その指摘を再発させないテストを足す。
