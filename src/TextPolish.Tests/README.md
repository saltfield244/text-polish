# 回帰テストと実機確認手順

対象: クリップボードの全形式退避・復元(v1.0.1 の不具合修正)、APIキーの暗号化保存、失敗時のログ出力、
ホットキーの連打・経路をまたいだ同時実行に対する排他、書き戻し先のウィンドウ検証、
LLM応答の終了理由の検査、整形パレットの結果状態、周辺文脈の送信ON/OFF。

## 自動テスト

外部NuGetパッケージを増やさない方針のため、xUnit等は使わず依存なしのコンソールアプリにしています。
失敗が1件でもあれば終了コード 1 を返します。

```
dotnet run --project src\TextPolish.Tests
```

- クリップボードのテストは**実際のクリップボードを書き換えます**。実行前の内容はテスト対象の
  `ClipboardSnapshot` で退避し、終了時に戻します。Windowsの「クリップボードの履歴」(Win+V)を
  有効にしている場合、テスト中の内容が履歴に残ります。
- クリップボードはOSの共有資源で、クリップボード履歴をはじめ他のプロセスも同時に開きます。
  テスト側で使っている WinForms の `Clipboard` はこの競合に弱く、短い間隔で読み書きすると
  書き込みが `ExternalException` で失敗したり、読み取りが空や壊れた値を返したりします。
  そのためテスト側の操作だけを短時間リトライしています(`ClipboardTests` の `Set` / `GetText` / `Query`)。
  検証対象の `ClipboardSnapshot` 側は変更していません。同じ往復を150回繰り返した計測では
  `WriteToClipboard` は毎回 `Written` を返し、復元内容も正しいことを確認しています。
- デスクトップのない環境(CI、サービス実行等)では `--no-clipboard` を付けて設定のテストだけを実行します。
  ```
  dotnet run --project src\TextPolish.Tests -- --no-clipboard
  ```

### Smart App Control が有効なPCでの実行

Smart App Control が有効な Windows では、`dotnet run` が
「アプリケーション制御ポリシーによってこのファイルがブロックされました」(0x800711C7)で
止まることがあります。署名のない `TextPolish.Core.dll` の読み込みが拒否されるためで、
コードの問題ではありません(イベント ビューアーの
`Microsoft-Windows-CodeIntegrity/Operational` に ID 3077 として残ります)。

単一ファイルとして発行すると、別DLLの読み込みが起きないため通ります。

```
dotnet publish -c Release -r win-x64 --self-contained false -p:PublishSingleFile=true -o publish\tests src\TextPolish.Tests\TextPolish.Tests.csproj
```

```
.\publish\tests\TextPolish.Tests.exe --no-clipboard
```

判定は発行先のパスごとに変わることがあり、同じ内容でも通る場所と通らない場所があります。
ブロックされたら発行先を変えて試してください。

開発機で Smart App Control を切る場合は、**その Windows の版で元に戻せるかを先に確認**して
ください。古い版では、一度切ると再インストールしない限り戻せません
(26H2 では戻せることを確認しています)。切らずに済ませるなら、上の単一ファイル発行か、
仮想マシン・Windows Sandbox で動かすほうが安全です。

### 手動確認用のLLMスタブ

実機確認の D・E・G は「整形中に別の操作をする」項目が多く、本物のAPIでは待ち時間が
毎回違うため手順を再現できません。`--stub` でLLMプロバイダのふりをするサーバーを立て、
アプリの `Endpoint` をそこへ向けると、応答の遅さと結果をその場で決められます。

```
dotnet run --project src\TextPolish.Tests -- --stub --delay 5000
```

立ち上がると `appsettings.json` に貼るURLを表示します。あとは標準入力で切り替えます
(`help` で一覧)。

| コマンド | 使う場面 |
|---|---|
| `delay 5000` | 「整形中」を5秒きっかり作る(D3・D4・E5・E6・E7・D11・D12) |
| `truncated` | 途中終了を返す(F1・F2・G5) |
| `nofinish` | 終了理由を返さないサーバーを再現する(F5) |
| `error` | 401 を返す。APIキーを壊さずに失敗を作れる(D8・G4) |
| `count` | 呼ばれた回数。3回押して1回しか呼ばれないことの確認(D1・D2) |
| `last` | 最後に送られた内容の要約。周辺文脈を送っていないかの確認(H1・H4) |

スタブはHTTPで待ち受けるため、`Endpoint` は `http://` になります。確認が終わったら
**元のエンドポイントに戻してください**。スタブで確認した項目は、本物のプロバイダの挙動を
確認したことにはなりません。記録には「スタブで確認」と明記します。

### 動いているアプリを UI Automation で覗く・操作する

実機確認のうち、画面を見て押す部分も自動で流せます。UIA2
(`System.Windows.Automation`。Windows デスクトップ SDK に入っているので外部NuGetは
増えません)を使い、アプリ本体が `ActiveWindowContextProvider` で使っているものと同じです。

```
dotnet run --project src\TextPolish.Tests -- --inspect
```

`--inspect` は**読み取りしかしません**。クリックもキー送出もしないので、誰かが同じアプリで
手作業の確認をしている最中でも流せます。例外は `--open-tray` だけで、通知領域の
「非表示のアイコンを表示する」を1回押します(アプリには触りません)。トレイアイコンは
隠れたアイコンの中にあると、開くまで UIA の木に現れません。

```
dotnet run --project src\TextPolish.Tests -- --drive palette --open --close
```

`--drive` は実際に操作します。**本物のクリックが飛ぶため、手作業の確認と同時には
流さないでください。**`--open` を付けると、文章の窓を自分で出してホットキーまで送るので、
人がどこかで文字を選んでおく必要はありません。

| 試作 | すること |
|---|---|
| `--drive palette` | 原文を読む・プリセットを切り替える・自由指示を入れる・有効無効を見る |
| `--drive tray` | トレイを右クリックして「設定」「終了」を辿る(D11・D12) |
| `--drive run` | 整形を走らせ、結果がスタブの返した文字列と一致するかを見る |
| `--drive quick` | 即実行のホットキーを連打し、1回しか整形されないことを見る(D1・D2) |
| `--drive d` | 実機確認の D1〜D10 を順に流す(`--drive d3` のように単独でも) |
| `--drive e` | 実機確認の E1〜E8 を順に流す(`--drive e3` のように単独でも) |

スタブと組み合わせると、次の形で流せます。`--expect-fail` は「採用しない応答のとき、
整形は終わるが書き戻せないままであること」を確かめます。

```
dotnet run --project src\TextPolish.Tests -- --drive run --open --close --expect-fail
```

| 応答 | 付ける引数 | 確かめること |
|---|---|---|
| `success` | `--expect <文字列>` | 結果がスタブの返した文字列と一致する |
| `success` + 待ち | `--cancel` | 整形中に中止すると待機へ戻り、結果は書き戻せない |
| `truncated` | `--expect-fail` | 途中終了を採用しない(F1・F2・G5) |
| `error` | `--expect-fail` | 401 でも落ちず、書き戻せない(D8・G4) |
| `malformed` | `--expect-fail` | 壊れたJSONでも落ちない |
| `nofinish` | `--expect <文字列>` | 終了理由が無くても整形できる(F5) |

**待ち時間を 0 にすると「整形中」を観測できません。** 整形中の確認をする回は、スタブの
`--delay` を 1500 以上にしてください。

**スタブを `dotnet run` で立てたままビルドすると失敗します。** 同じ exe を掴むためです。
`bin` の複製を別フォルダへ置いて、そこから立ててください。

**スタブは受け取るたびに1行出します**(`[n件目] POST ... / 本文 N 文字`)。
「押したのに来ていない」「2回来ている」はこれで分かります。

### D を自分で流すときの注意

```
dotnet run --project src\TextPolish.Tests -- --drive d --expect STUB-RESULT-XXXX
```

- **D8 は `--outcome error` のスタブが必要です。** 成功を返すスタブのまま流すと
  「失敗が記録されない」と出ます(通し運転からは外してあります)
- **ほかのアプリが前面を奪うと判定できません。** 送る直前に前面と選択を確かめ、
  送った直後にも前面を確かめます。奪われた回は「判定できず」として、アプリの
  不合格とは別に数えます。混ぜると環境のせいの失敗を不具合として読んでしまいます
  (実際に読みかけました。相手は RustDesk でした)
- **D1 の「無視しました」が2件になることは、合成入力では確認できません。**
  押す回数と間隔をいろいろ変えても必ず1件で、3回目以降はログに残りません。
  2回目が無視されることは確認できるので、判定はそこまでにしています。
  件数の一致は人の指で確かめてください

### E を自分で流すときの注意

```
dotnet run --project src\TextPolish.Tests -- --drive e --expect STUB-RESULT-XXXX
```

- **取得元の窓と、別の窓の2枚を試作が自分で出します。** 別の窓(「試作B(別の窓)」)は
  貼られてはいけない側です。判定の軸は「Bの中身が変わっていないこと」で、
  ここが崩れたときだけ不具合として扱います
- **E3・E6 は中止になりません。** 書き戻しは貼る前に取得元へフォーカスを戻すため、
  途中で別の窓を前面にしても、取得元が生きていれば戻して貼るのが設計どおりです。
  試作はどちらの経路になったかを出すだけにしています(下の表の注記も参照)
- **整形中に手を出す回(E5・E6)はスタブの `--delay` を 3000 以上にしてください。**
  応答が速いと、別の窓を前面にする前に書き戻しが終わってしまいます

`--drive run` / `--drive d` / `--drive e` は `appsettings.json` の `Endpoint` が
ループバックでなければ**拒否します**。
本物のプロバイダを呼ぶと課金され、応答時間も揃わないためです。先に `--stub` を立てて
`Endpoint` を向けてください。

**「置き換える」は押しません。** 押すと利用者が書いた文章が置き換わるためです。
`--drive quick`(即実行)は書き戻しまで通りますが、貼り付け先は試作が出した自前の窓だけです。
原文と整形結果も画面に出しません(長さと一致判定だけを出します)。

UIA から何が見えるかは実測しました。自動化を足すときの前提になります。

| 要素 | 引き方 | できること |
|---|---|---|
| 実行 | `AutomationId=RunButton` | Invoke |
| 置き換える | `AutomationId=ApplyButton` | Invoke。結果が無い間は無効 |
| キャンセル | `AutomationId=CloseButton` | Invoke |
| 差分表示 | `AutomationId=ShowDiffCheckBox` | Toggle。結果が無い間は無効 |
| 選択中のテキスト | `AutomationId=OriginalTextBox` | Value で読める |
| 整形結果 | `AutomationId=ResultTextBox` | Value で読める |
| 自由指示 | `AutomationId=InstructionBox` | Value で読み書き。履歴は ItemContainer |
| プリセット | 名前(「整える」等)**と種類** | Toggle。AutomationId は無い |
| トレイアイコン | 名前の部分一致 | Invoke(左クリック相当)。右クリックは座標が必要 |
| トレイメニュー | 項目名 | Invoke |

注意が3つあります。

- **プリセットは種類で絞らないと引けません。** 同じ名前の `TextBlock` が隣にいて、
  名前だけで引くとそちらを掴みます。`TextBlock` は Toggle を持たないため、
  掴み間違えると後段で失敗して原因が分かりにくくなります
- **トレイアイコンの名前は完全一致では引けません。** `SetStatus` が状態を後ろに足します
  (「テキスト整形ツール - 整形中...」)
- **トレイの座標は開くたびに変わります。** `BoundingRectangle` は押す直前に取り直します

有効・無効が UIA から見えるので、「整形中は押せない」「結果が無い間は置き換えられない」は

テストで固定できますが、**実際のフォーカス移動・キー送出・LLMの応答は含みません**。
そこは下記 E〜H の実機確認で見ます。

排他のテストは `OperationGate` と、App 側の呼び出し方(パレットは閉じるまで保持、即実行は
`finally` で解放)を模した流れを対象にしています。ホットキーのフックとWPFのウィンドウは
自動化できないため、実際のキー入力での挙動は下記 D の実機確認で見ます。

Ctrl+C/Ctrl+V の送出を伴う端から端までの動作(`SelectionCapture` / `ClipboardTextInserter`)は、
フォアグラウンドのウィンドウに依存して自動化が不安定になるため、下記の実機確認で見ます。

## Windows実機での確認手順

準備: `dotnet build` したアプリ(または publish した配布物)を起動し、ログ
(`%AppData%\TextPolish\logs\`)を開いておく。メモ帳とエクスプローラー、ペイント、Word か ブラウザを使う。

### A. クリップボードの保持

各項目とも「整形パレットで整形して書き戻す」と「即実行ホットキー」の両方で確認する。
書き戻しの約1秒後(`RestoreDelayMs`)に、元の内容に戻っていることを確かめる。

| # | 操作前にクリップボードへ入れるもの | 確認方法 | 期待結果 |
|---|---|---|---|
| A1 | メモ帳でコピーしたテキスト | メモ帳に貼り付け | 元のテキストが貼り付く |
| A2 | Snipping Tool / PrtScn の画像 | ペイントに貼り付け | 元の画像が貼り付く |
| A3 | エクスプローラーで「コピー」したファイル2つ | 別フォルダで貼り付け | 2つともコピーされる |
| A4 | エクスプローラーで「切り取り」したファイル | 別フォルダで貼り付け | **移動**になる(コピーにならない) |
| A5 | ブラウザ/Wordで書式付きの文章をコピー | Wordに貼り付け | 太字・リンク等の書式が残る(HTML/RTF) |
| A6 | Excel のセル範囲 | Excel に貼り付け | セル範囲として貼り付く |
| A7 | クリップボードを空にする(`powershell -sta -c "Add-Type -A System.Windows.Forms; [Windows.Forms.Clipboard]::Clear()"`) | メモ帳で Ctrl+V | 何も貼り付かない |
| A8 | テキストを選択せずにホットキー | — | 「テキストが選択されていません」の通知。クリップボードは元のまま |

### B. 復元待ち中の競合

| # | 操作 | 期待結果 |
|---|---|---|
| B1 | 設定の `RestoreDelayMs` を 5000 にする。即実行で書き戻した直後(5秒以内)に、別のテキストを Ctrl+C | 5秒後もクリップボードは自分がコピーしたテキストのまま。ログに「復元は見送りました」 |
| B2 | (B1の設定のまま) 元の内容Xをコピー → 即実行 → 5秒以内にもう一度即実行 | 最終的にクリップボードはX(整形結果1が残らない)。ログに「復元待ちを引き継ぎます」 |
| B3 | (B1の設定のまま) 即実行の直後にトレイから終了 | 終了後のクリップボードは元の内容 |

| B5 | 4K画面全体のスクリーンショットをコピーしてから即実行 | 体感で遅くならない。画像が戻る |

移行後にプロバイダ側でキーを再発行(ローテーション)してください。

### D. ホットキーの連打・同時実行

準備: ログ(`%AppData%\TextPolish\logs\`)を開いておく。無視された操作は
「ほかの操作(…)が実行中のため、…を無視しました。」としてログに残る。
D3・D4 は差が見えるよう、LLMの応答が数秒かかるモデル・長い文章で試す。

| # | 操作 | 期待結果 |
|---|---|---|
| D1 | メモ帳でテキストを選択し、パレットのホットキーを素早く3回押す | パレットは1つだけ開く。ログに「整形パレットを無視しました」が2件。メモ帳の選択・クリップボードの内容は壊れない |
| D2 | テキストを選択し、即実行のホットキーを素早く3回押す | 整形・書き戻しは1回だけ。ログに「即実行を無視しました」が2件。整形結果が二重に貼り付かない |
| D3 | テキストを選択して即実行 → 整形中(トレイが「…で整形中...」)にパレットのホットキーを押す | パレットは開かない。即実行の書き戻しが正常に完了する。ログに「整形パレットを無視しました」 |
| D4 | パレットを開いた状態で即実行のホットキーを押す | 何も起こらない。ログに「即実行を無視しました」。パレットはそのまま使える |
| D5 | パレットを開いた状態でパレットのホットキーを押す | パレットが前面に出るだけ(新しく開かない) |
| D6 | パレットの選択テキスト取得中(押してすぐの0.1秒以内)に、即実行のホットキーを押す | 即実行は無視される。Ctrl+C の送出は1回だけで、パレットには選択したテキストがそのまま入る |
| D7 | テキストを選択せずにパレット/即実行のホットキーをそれぞれ3回押す | 毎回「テキストが選択されていません」の通知が出る(排他が残って2回目以降が無反応にならない) |
| D8 | APIキーを誤った値にして即実行 → エラー通知が出たあと、もう一度即実行 | 2回目も通知が出る(例外で排他が残らない) |
| D9 | パレットを開き、整形を実行してから結果を適用せずに閉じる → 即実行 | 即実行が動く(パレットを閉じた時点で解放されている) |
| D10 | パレット→即実行→パレット→即実行を10回繰り返す | 毎回動く。無視のログが出ない。クリップボードは元の内容に戻る |
| D11 | 即実行の整形中にトレイから設定画面を開き、保存して閉じる | 即実行は完了する。閉じたあとのホットキーが効く |
| D12 | 即実行の整形中にトレイから終了 | 終了できる。クリップボードは元の内容に戻る(`OnExit` の即時復元) |

### E. 書き戻し先の検証(意図しないウィンドウへ貼り付けない)

準備: メモ帳とブラウザ(または別のメモ帳)を2つ開き、ログを開いておく。
`RequestTimeoutSeconds` は既定のまま、LLMの応答が数秒かかるモデルを使う。

| # | 操作 | 期待結果 |
|---|---|---|
| E1 | メモ帳でテキストを選択 → パレットで整形 → 「置き換える」 | 選択範囲が整形結果に置き換わる(従来どおり) |
| E2 | パレットで整形したあと、**元のメモ帳を閉じて**から「置き換える」 | どこにも貼り付かない。パレットが出し直され「書き戻し先が元のウィンドウではなくなっていた」と表示。整形結果は残っている |
| E3 | パレットで整形したあと、**別のウィンドウをクリックして前面にしてから**パレットの「置き換える」 | 別のウィンドウには貼り付かない。元のメモ帳が前面に戻され、そこへ整形結果が貼り付く(※) |
| E4 | E3 のあと、元のメモ帳をクリックして選択し直し、パレットの「置き換える」を押す | 今度は正しく置き換わる(再試行できる) |
| E5 | 即実行でテキストを整形中(トレイが「…で整形中...」)に、**元のアプリを閉じる** | 書き戻しは行われない。「元のウィンドウへ戻せませんでした」の通知が出て、整形結果がクリップボードに入っている(メモ帳で Ctrl+V して確認) |
| E6 | 即実行で整形中に、**別のアプリをクリックして前面にする** | 別のアプリには貼り付かない。元のアプリへ戻して貼り付くか、戻せなければ通知が出て整形結果がクリップボードに入る(※) |
| E7 | 即実行で、整形中に何もせず待つ(通常の使い方) | 従来どおり選択範囲が置き換わる。ログに「貼り付け先が…」の中止ログが出ない |
| E8 | E2・E3 の直後にクリップボードを貼り付ける | **整形結果ではなく、元のクリップボード内容**が貼り付く(中止時は元に戻す) |

※ E3・E6 で**中止されるとは限りません。** 書き戻しは貼る前に取得元のウィンドウへ
フォーカスを戻すため(`WindowFocus.RestoreAsync`)、別のウィンドウを前面にしただけで
あれば、取得元へ戻して貼るのが設計どおりの動きです。中止になるのは取得元へ戻せない
とき(閉じられた・最小化で戻せない)だけです。どちらの場合も**別のウィンドウへは
貼り付きません**。ここが守られていることが確認の目的です。E4 は中止された場合の
やり直しなので、貼り付いた場合は不要です。

E5・E6 では、整形結果を失わないかわりに元のクリップボード内容が上書きされます。
ログに「整形結果をクリップボードへ退避しました(元の内容は上書きされます)」が出ることも確認してください。

### F. LLM応答の途中終了

準備: 設定画面か `appsettings.json` で、使っているプロバイダの `MaxCompletionTokens` を
`16` のように極端に小さくする(応答が確実に途中で切れる値)。

| # | 操作 | 期待結果 |
|---|---|---|
| F1 | 長めの文章を選択してパレットで整形 | 整形結果は表示されず「整形結果が出力途中で打ち切られました(終了理由: length)」と出る。「置き換える」は押せない |
| F2 | 同じ状態で**即実行** | **原文は変わらない**。「整形に失敗しました: 整形結果が出力途中で…」の通知が出る |
| F3 | `MaxCompletionTokens` を既定(null)に戻して整形 | 従来どおり整形できる。ログに「finish_reason がありませんでした」が出ない(stopが返っている) |
| F4 | Gemini を使い、F1・F2 を繰り返す | 同様に採用されない(`finishReason=MAX_TOKENS`) |
| F5 | ローカルのOpenAI互換サーバーなど `finish_reason` を返さない環境で整形 | 整形できる。ログに「finish_reason がありませんでした。正常終了として扱います」が出る |
| F6 | F1・F2 のあと `%AppData%\TextPolish\logs\` の当日ログを開く | 整形を依頼した文章が1文字も載っていない。残っているのは `判定=Truncated finish_reason=length BodyChars=...` のような診断情報だけ |
| F7 | APIキーを誤った値にして即実行 → 同じログを開く | `Status=401` とエラー種別は残るが、APIキーと応答本文は載っていない(Geminiは `?key=` が `(秘匿)` になる) |
| F8 | 日付が変わるまでアプリを起動したままにして、整形してからログフォルダを見る | 前日の `app-YYYYMMDD.log` ではなく、当日の日付のファイルに書かれている |
| F9 | パレットで整形を実行して「中止」を押し、同じログを開く | 中止は INFO で1行残るだけで、ERROR が出ていない |

F5 は `--stub` でスタブを立て、`nofinish` に切り替えれば再現できます(環境を探す必要はありません)。
F1・F2 は、途中終了を採用しないことが今回の修正の要点なので省略しないでください。

### H. 周辺文脈の送信ON/OFF

準備: メモ帳に数段落の文章を書き、その一部だけを選択して整形する。
ログに「周辺文脈: …」の行が出るので、それで送信の有無を確認する。

| # | 操作 | 期待結果 |
|---|---|---|
| H1 | 更新後そのまま(既定)で整形 | ログが「周辺文脈: 送信しない設定(SendSurroundingContext=false)」。整形はできる |
| H2 | 設定画面「LLMへ送る範囲」をオンにして保存 → 整形 | ログが「周辺文脈: N文字」。`appsettings.json` の `SendSurroundingContext` が `true` になっている |
| H3 | H2 の状態でアプリを再起動して整形 | オンのまま維持される |
| H4 | オフに戻して、UI Automation に対応したアプリ(メモ帳・Word等)で整形 | ログが「送信しない設定」。周辺の文章が送られない |
| H5 | オン・オフの両方で、ログの「アクティブアプリ: ...」にアプリ名が出る | どちらでもアプリ名は取得され、プロンプトに含まれる(アプリ名による文体の切り分けはこの情報に依存するため) |

H2 でオンにしたあと、意図せずオンのまま使い続けないよう、確認後はオフに戻すか
意識的にオンを選んでください。

なお `Formatting.AppStyleRules` によるアプリごとの文体指示は、v1.0.2 時点でも
意図的に配線していません(IMPLEMENTATION-NOTES.md「見送ったもの」参照)。
今回の変更で影響を受けるのは「アプリ名をプロンプトへ渡すかどうか」ではなく、
「周辺の未選択テキストを渡すかどうか」だけで、アプリ名は常に渡します。
