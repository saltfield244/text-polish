# 回帰テストと実機確認手順

対象: クリップボードの全形式退避・復元(v1.0.1 の不具合修正)、APIキーの暗号化保存、失敗時のログ出力、
ホットキーの連打・経路をまたいだ同時実行に対する排他、書き戻し先のウィンドウ検証、
LLM応答の終了理由の検査、整形パレットの結果状態、周辺文脈の送信ON/OFF。

## 自動テスト

外部NuGetパッケージを増やさない方針のため、xUnit等は使わず依存なしのコンソールアプリにしています。
失敗が1件でもあれば終了コード 1 を返します。

```
dotnet run --project src\TextPolish.Tests
```

- クリップボードのテストは**実際のクリップボードを書き換えます**。実行前の内容はテスト対象の
  `ClipboardSnapshot` で退避し、終了時に戻します。Windowsの「クリップボードの履歴」(Win+V)を
  有効にしている場合、テスト中の内容が履歴に残ります。
- クリップボードはOSの共有資源で、クリップボード履歴をはじめ他のプロセスも同時に開きます。
  テスト側で使っている WinForms の `Clipboard` はこの競合に弱く、短い間隔で読み書きすると
  書き込みが `ExternalException` で失敗したり、読み取りが空や壊れた値を返したりします。
  そのためテスト側の操作だけを短時間リトライしています(`ClipboardTests` の `Set` / `GetText` / `Query`)。
  検証対象の `ClipboardSnapshot` 側は変更していません。同じ往復を150回繰り返した計測では
  `WriteToClipboard` は毎回 `Written` を返し、復元内容も正しいことを確認しています。
- デスクトップのない環境(CI、サービス実行等)では `--no-clipboard` を付けて設定のテストだけを実行します。
  ```
  dotnet run --project src\TextPolish.Tests -- --no-clipboard
  ```
- **GitHub Actions で流れているときは、失敗したテスト名を注記(annotation)として出します**
  (`GITHUB_ACTIONS=true` のときだけ。手元の実行では何も出ません)。
  実行ログは公開リポジトリでも**サインインしないと読めない**一方、注記はコミットの
  チェック画面とメール通知に出るため、ログを開かずに「どのテストが落ちたか」を追えます。
  わざと1件落として、注記が出ることを確かめてあります。
- **時間を測るテストは、タイマーの刻みぶんを許容します。** Windows のタイマーは既定で
  約15.6ms刻みで、`Task.Delay` は1刻みぶん早く起きえます。「スタブ: 指定した時間だけ
  応答を遅らせる」は厳密な比較にしていたため、CI で「391ms < 400ms」で落ちました
  (2026-11-20、run #19・#18)。50ms を許容する形に直しています。
  見たいのは遅延が効いていることであって精度ではないので、
  遅延を外すと今でも落ちることを確かめたうえで緩めました。

### Smart App Control が有効なPCでの実行

Smart App Control が有効な Windows では、`dotnet run` が
「アプリケーション制御ポリシーによってこのファイルがブロックされました」(0x800711C7)で
止まることがあります。署名のない `TextPolish.Core.dll` の読み込みが拒否されるためで、
コードの問題ではありません(イベント ビューアーの
`Microsoft-Windows-CodeIntegrity/Operational` に ID 3077 として残ります)。

単一ファイルとして発行すると、別DLLの読み込みが起きないため通ります。

```
dotnet publish -c Release -r win-x64 --self-contained false -p:PublishSingleFile=true -o publish\tests src\TextPolish.Tests\TextPolish.Tests.csproj
```

```
.\publish\tests\TextPolish.Tests.exe --no-clipboard
```

判定は発行先のパスごとに変わることがあり、同じ内容でも通る場所と通らない場所があります。
ブロックされたら発行先を変えて試してください。

開発機で Smart App Control を切る場合は、**その Windows の版で元に戻せるかを先に確認**して
ください。古い版では、一度切ると再インストールしない限り戻せません
(26H2 では戻せることを確認しています)。切らずに済ませるなら、上の単一ファイル発行か、
仮想マシン・Windows Sandbox で動かすほうが安全です。

### 手動確認用のLLMスタブ

実機確認の D・E・G は「整形中に別の操作をする」項目が多く、本物のAPIでは待ち時間が
毎回違うため手順を再現できません。`--stub` でLLMプロバイダのふりをするサーバーを立て、
アプリの `Endpoint` をそこへ向けると、応答の遅さと結果をその場で決められます。

```
dotnet run --project src\TextPolish.Tests -- --stub --delay 5000
```

立ち上がると `appsettings.json` に貼るURLを表示します。あとは標準入力で切り替えます
(`help` で一覧)。

| コマンド | 使う場面 |
|---|---|
| `delay 5000` | 「整形中」を5秒きっかり作る(D3・D4・E5・E6・E7・D11・D12) |
| `truncated` | 途中終了を返す(F1・F2・G5) |
| `nofinish` | 終了理由を返さないサーバーを再現する(F5) |
| `error` | 401 を返す。APIキーを壊さずに失敗を作れる(D8・G4) |
| `count` | 呼ばれた回数。3回押して1回しか呼ばれないことの確認(D1・D2) |
| `last` | 最後に送られた内容の要約。周辺文脈を送っていないかの確認(H1・H4) |

スタブはHTTPで待ち受けるため、`Endpoint` は `http://` になります。確認が終わったら
**元のエンドポイントに戻してください**。スタブで確認した項目は、本物のプロバイダの挙動を
確認したことにはなりません。記録には「スタブで確認」と明記します。

### 動いているアプリを UI Automation で覗く・操作する

実機確認のうち、画面を見て押す部分も自動で流せます。UIA2
(`System.Windows.Automation`。Windows デスクトップ SDK に入っているので外部NuGetは
増えません)を使い、アプリ本体が `ActiveWindowContextProvider` で使っているものと同じです。

```
dotnet run --project src\TextPolish.Tests -- --inspect
```

`--inspect` は**読み取りしかしません**。クリックもキー送出もしないので、誰かが同じアプリで
手作業の確認をしている最中でも流せます。例外は `--open-tray` だけで、通知領域の
「非表示のアイコンを表示する」を1回押します(アプリには触りません)。トレイアイコンは
隠れたアイコンの中にあると、開くまで UIA の木に現れません。

```
dotnet run --project src\TextPolish.Tests -- --drive palette --open --close
```

`--drive` は実際に操作します。**本物のクリックが飛ぶため、手作業の確認と同時には
流さないでください。**`--open` を付けると、文章の窓を自分で出してホットキーまで送るので、
人がどこかで文字を選んでおく必要はありません。

| 試作 | すること |
|---|---|
| `--drive palette` | 原文を読む・プリセットを切り替える・自由指示を入れる・有効無効を見る |
| `--drive tray` | トレイを右クリックして、出たメニューを読む(押さない。D11・D12 の足場) |
| `--drive run` | 整形を走らせ、結果がスタブの返した文字列と一致するかを見る |
| `--drive quick` | 即実行のホットキーを連打し、1回しか整形されないことを見る(D1・D2) |
| `--drive d` | 実機確認の D1〜D12 を順に流す(`--drive d3` のように単独でも) |
| `--drive e` | 実機確認の E1〜E8 を順に流す(`--drive e3` のように単独でも) |
| `--drive g` | 実機確認の G1〜G6 を順に流す(`--drive g3` のように単独でも) |
| `--drive f` | 実機確認の F(F1・F2・F3・F5・F6・F9)を順に流す(`--drive f6` のように単独でも) |
| `--drive h` | 実機確認の H1〜H5 を順に流す(`--drive h2` のように単独でも) |
| `--drive i` | 実機確認の I1〜I4(自由指示の履歴)を順に流す(`--drive i2` のように単独でも) |
| `--drive j` | 実機確認の J1・J2(送信先の検査)を流す(`--drive j1` のように単独でも) |
| `--allow-real` | ループバック以外の Endpoint でも `run`・`quick` を通す(本物を呼ぶ。F7 用) |

スタブと組み合わせると、次の形で流せます。`--expect-fail` は「採用しない応答のとき、
整形は終わるが書き戻せないままであること」を確かめます。

```
dotnet run --project src\TextPolish.Tests -- --drive run --open --close --expect-fail
```

| 応答 | 付ける引数 | 確かめること |
|---|---|---|
| `success` | `--expect <文字列>` | 結果がスタブの返した文字列と一致する |
| `success` + 待ち | `--cancel` | 整形中に中止すると待機へ戻り、結果は書き戻せない |
| `truncated` | `--expect-fail` | 途中終了を採用しない(F1・F2・G5) |
| `error` | `--expect-fail` | 401 でも落ちず、書き戻せない(D8・G4) |
| `malformed` | `--expect-fail` | 壊れたJSONでも落ちない |
| `nofinish` | `--expect <文字列>` | 終了理由が無くても整形できる(F5) |

**待ち時間を 0 にすると「整形中」を観測できません。** 整形中の確認をする回は、スタブの
`--delay` を 1500 以上にしてください。

**スタブを `dotnet run` で立てたままビルドすると失敗します。** 同じ exe を掴むためです。
`bin` の複製を別フォルダへ置いて、そこから立ててください。

**スタブは受け取るたびに1行出します**(`[n件目] POST ... / 本文 N 文字`)。
「押したのに来ていない」「2回来ている」はこれで分かります。

### D を自分で流すときの注意

```
dotnet run --project src\TextPolish.Tests -- --drive d --expect STUB-RESULT-XXXX
```

- **D8 は `--outcome error` のスタブが必要です。** 成功を返すスタブのまま流すと
  「失敗が記録されない」と出ます(通し運転からは外してあります)
- **ほかのアプリが前面を奪うと判定できません。** 送る直前に前面と選択を確かめ、
  送った直後にも前面を確かめます。奪われた回は「判定できず」として、アプリの
  不合格とは別に数えます。混ぜると環境のせいの失敗を不具合として読んでしまいます
  (実際に読みかけました。相手は RustDesk でした)
- **D1 の「無視しました」が2件になることは、合成入力では確認できません。**
  押す回数と間隔をいろいろ変えても必ず1件で、3回目以降はログに残りません。
  2回目が無視されることは確認できるので、判定はそこまでにしています。
  件数の一致は人の指で確かめてください
- **D11・D12 を含めるときは、スタブの `--delay` を 8000 にしてください。** どちらも
  「整形中にトレイを操作する」項目で、トレイのメニューを出して項目を押すまでに数秒かかります。
  応答が速いと、操作する前に整形が終わってしまいます
- **D11 の「保存」は、実際に `appsettings.json` を書き換えます。** 手順どおり保存して
  閉じるところまで見るため避けられません。確認が終わったら設定ファイルを戻してください
- **D12 はアプリを終了させます。** 通し運転では最後にまわし、確認のあと試作が起こし直します
  (起こし直したプロセスは別のIDになるため、D12 より後に流す項目は作っていません)
- **メニューの項目は UIA の Invoke では押しません。** Invoke は相手の処理が返るまで待つため、
  モーダルのダイアログを出す「設定」ではダイアログを閉じるまで返らず、UIA が時間切れになります
  (実際に COMException で落ちました)。「終了」も待っている相手が消えます。
  人と同じように座標で左クリックし、結果は画面とプロセスで確かめます

### E を自分で流すときの注意

```
dotnet run --project src\TextPolish.Tests -- --drive e --expect STUB-RESULT-XXXX
```

- **取得元の窓と、別の窓の2枚を試作が自分で出します。** 別の窓(「試作B(別の窓)」)は
  貼られてはいけない側です。判定の軸は「Bの中身が変わっていないこと」で、
  ここが崩れたときだけ不具合として扱います
- **E3・E6 は中止になりません。** 書き戻しは貼る前に取得元へフォーカスを戻すため、
  途中で別の窓を前面にしても、取得元が生きていれば戻して貼るのが設計どおりです。
  試作はどちらの経路になったかを出すだけにしています(下の表の注記も参照)
- **整形中に手を出す回(E5・E6)はスタブの `--delay` を 3000 以上にしてください。**
  応答が速いと、別の窓を前面にする前に書き戻しが終わってしまいます

### G を自分で流すときの注意

```
dotnet run --project src\TextPolish.Tests -- --drive g
```

- **G はスタブを自分で立てます。`--stub` は止めてから流してください。** G は
  「1回目は成功、2回目は失敗」のように応答を回ごとに変える必要があり、別プロセスの
  スタブでは標準入力で手打ちしない限り切り替えられません。ポート番号はアプリの
  `appsettings.json` の `Endpoint` から読むので、向け先を先に合わせてください
- **`--expect` は要りません。** 返す文字列は項目ごとに試作が決めます(1回目と2回目で
  違う文字列を返し、書き戻ったのがどちらかを見分けるため)
- **G4・G5 は設定を変えずにスタブで作ります。** README の手順はAPIキーを誤った値に
  する・`MaxCompletionTokens` を小さくするですが、アプリから見た条件は同じ
  (401 が返る・途中終了が返る)なので、設定ファイルを触らずに済ませています

`--drive run` / `--drive d` / `--drive e` / `--drive g` / `--drive f` / `--drive h` は
`appsettings.json` の `Endpoint` がループバックでなければ**拒否します**。
本物のプロバイダを呼ぶと課金され、応答時間も揃わないためです。先に `--stub` を立てて
`Endpoint` を向けてください。

例外は `--allow-real` を付けたときだけです。F7(誤った鍵で失敗を受ける)や、本物の鍵で
一度だけ整形してみる確認は、本物のエンドポイントへ投げないと成り立ちません。付けると
`--drive run` と `--drive quick` だけが通り、何へ向いているかを画面に出します。
**付け忘れで課金されることがないよう、既定は拒否のままです。** 通し運転(D・E・G)には
この抜け道はありません。

`--drive i` と `--drive j` だけは例外で、Endpoint を見ません。整形を一度も走らせず、
設定画面とファイルしか触らないためです(LLMへは何も飛びません)。

**「置き換える」は押しません。** 押すと利用者が書いた文章が置き換わるためです。
`--drive quick`(即実行)は書き戻しまで通りますが、貼り付け先は試作が出した自前の窓だけです。
原文と整形結果も画面に出しません(長さと一致判定だけを出します)。

UIA から何が見えるかは実測しました。自動化を足すときの前提になります。

| 要素 | 引き方 | できること |
|---|---|---|
| 実行 | `AutomationId=RunButton` | Invoke |
| 置き換える | `AutomationId=ApplyButton` | Invoke。結果が無い間は無効 |
| キャンセル | `AutomationId=CloseButton` | Invoke |
| 差分表示 | `AutomationId=ShowDiffCheckBox` | Toggle。結果が無い間は無効 |
| 選択中のテキスト | `AutomationId=OriginalTextBox` | Value で読める |
| 整形結果 | `AutomationId=ResultTextBox` | Value で読める |
| 自由指示 | `AutomationId=InstructionBox` | Value で読み書き。履歴は ItemContainer |
| プリセット | 名前(「整える」等)**と種類** | Toggle。AutomationId は無い |
| トレイアイコン | 名前の部分一致 | Invoke(左クリック相当)。右クリックは座標が必要 |
| トレイメニュー | 項目名 | Invoke |

注意が3つあります。

- **プリセットは種類で絞らないと引けません。** 同じ名前の `TextBlock` が隣にいて、
  名前だけで引くとそちらを掴みます。`TextBlock` は Toggle を持たないため、
  掴み間違えると後段で失敗して原因が分かりにくくなります
- **トレイアイコンの名前は完全一致では引けません。** `SetStatus` が状態を後ろに足します
  (「テキスト整形ツール - 整形中...」)
- **トレイの座標は開くたびに変わります。** `BoundingRectangle` は押す直前に取り直します

有効・無効が UIA から見えるので、「整形中は押せない」「結果が無い間は置き換えられない」は
ログではなく `IsEnabled` で直接確かめられます。

| 区分 | 確認していること |
|---|---|
| 設定 | v1.0.1 の平文 `ApiKey` を3プロバイダとも暗号化して移行し、ファイルに平文が残らない |
| 設定 | 移行でAPIキー以外の設定(ホットキー・モデル名等)が変わらない |
| 設定 | テンプレートの `TODO-...` は暗号化せず、読み込みだけではファイルを書き換えない |
| 設定 | ファイルの `ApiKey` を直接書き換えた場合はそれが優先され、再暗号化される |
| 設定 | 設定画面からの更新・削除 |
| 設定 | 復号できない暗号文は、保存しても「削除」を押すまで消えない |
| 設定 | 別プロバイダの暗号文を書き写しても復号できない |
| 設定 | 保存に失敗しても元のファイルは変わらず、一時ファイルも残らない |
| 設定 | 5000文字のトークン・非ASCIIのキーの往復 |
| クリップボード | テキスト / テキスト+HTML+RTF / 画像 / ファイル一覧(切り取り・コピーの区別を含む) / 空 の復元 |
| クリップボード | サイズ上限を超えた場合は小さい形式(テキスト等)を優先して残す |
| 遅延復元 | 待ち時間後に元の内容へ戻る |
| 遅延復元 | 待機中にユーザーがコピーした内容を上書きしない |
| 遅延復元 | 連続実行しても、最後に残るのは最初の元内容 |
| 遅延復元 | アプリ終了時は待たずに復元する |
| 排他 | 保持中の再取得は失敗する(ホットキーの連打) |
| 排他 | 選択テキストの取得を始める前から保持する(パレットのウィンドウ生成を待たない) |
| 排他 | 即実行の整形中はパレットを起動しない / パレット表示中は即実行しない |
| 排他 | 例外・キャンセル・選択テキストなしのいずれでも解放される |
| 排他 | 二重解放しても、間に始まった操作の排他を解かない |
| 排他 | 交互操作を繰り返しても取りこぼさない |
| 排他 | 複数スレッドから同時に取得しても成功するのは1件 |
| 書き戻し先 | 取得元が前面なら送出 / 別ウィンドウ・閉じられている場合は中止 |
| 書き戻し先 | 取得元が分からない場合は照合しない |
| 書き戻し先 | 存在しないウィンドウへはフォーカス復帰を試みず即座に失敗する |
| 書き戻し先 | 照合に失敗したら Ctrl+V を送らず、クリップボードを元の内容へ戻す |
| 応答判定 | OpenAI互換・Azure: stop は採用、length / content_filter / 未知の理由は採用しない |
| 応答判定 | finish_reason が無い応答は、本文があれば採用する(省略するサーバーがあるため) |
| 応答判定 | 本文が空なら採用しない。空かつ length なら出力上限として知らせる |
| 応答判定 | Gemini: STOP は採用、MAX_TOKENS / SAFETY は採用しない |

C8(起動しただけでは書き換わらない)と混ぜないよう分けて書いています。2026-11-20 実測。

移行後も、ディスクの空き領域やバックアップ・OneDriveの版履歴・ボリュームシャドウコピーには
平文の旧ファイルが残っている可能性があります。キーが漏れた可能性を排除したい場合は、
移行後にプロバイダ側でキーを再発行(ローテーション)してください。

`RequestTimeoutSeconds` は既定のまま、LLMの応答が数秒かかるモデルを使う。

| # | 操作 | 期待結果 |

貼り付きません**。ここが守られていることが確認の目的です。E4 は中止された場合の
やり直しなので、貼り付いた場合は不要です。

F1・F2・F3・F5・F6・F9 は `--drive f` で流せます(2026-11-20 実測、全部期待どおり)。
F は項目ごとに応答の種類を変えるため、**スタブは試作の中で立てます。`--stub` は止めてから
流してください。** F5 の「終了理由を返さない環境」も、そのスタブで作ります
(環境を探す必要はありません)。

`--drive f` で見ていることのうち、手順書では目で確かめていた部分:

- F6 は原文の断片4種・`Body=`・APIキーの形・「全行が時刻で始まること」を機械的に照合します
  (`LogFileAssert`)。`判定=` / `BodyChars=` のような診断情報が**残っている**ことも見ます
- F9 は中止の行が INFO であることと、その間に ERROR が1件も無いことを見ます
- F3 は手順書では `MaxCompletionTokens` を既定へ戻す形ですが、要点は「終了理由が返るときに
  正常として扱えること」なので、スタブの正常応答で同じ状態を作っています。
  設定値そのものを変える確認は省いています

F1・F2 は、途中終了を採用しないことが v1.0.2 の修正の要点なので省略しないでください。

**F7 で Gemini のログに出ることの実測(2026-11-20、本物の鍵と誤った鍵の両方)**

- **URL 自体がログに出ないため、`?key=` を隠す場面はそもそも来ません。**

- なお 2026-11-20 に、APIキーの渡し方を `?key=` から `x-goog-api-key` ヘッダーへ
  変えました(同じ手順で、本物の鍵で整形が通ることを確認済み)。URLにキーが乗らないため、
  例外のメッセージやプロキシのアクセスログにも残りません

- 本物の鍵でも、割当てが無いプロジェクトでは `Status=402 ErrorStatus=RESOURCE_EXHAUSTED`。
  鍵が通っているかどうかは、このエラー種別の違いで見分けられます
  (`INVALID_ARGUMENT` = 鍵が不正、`RESOURCE_EXHAUSTED` = 鍵は通って割当てで止まった、
  `NOT_FOUND` = 鍵も割当ても通っていてモデル名が無い)

**Gemini で実際に整形できることの実測(2026-11-20、本物の鍵)**

| 経路 | 結果 |
|---|---|
| 即実行 | 書き戻しまで成功(34文字 → 28文字)。ログは文字数と送出先プロセスだけ |
| パレット | 「実行」→「中止」表示→完了で「置き換える」が押せる状態まで。書き換え率も出る |

- **`gemini-2.5-flash` と `gemini-2.0-flash` は 404 NOT_FOUND。** 2.5系は 2026-10-20 に廃止され、
  2.0系も使えません。配布時のテンプレートの `TODO-model` を埋めるときは、
  その時点で生きているモデル名を確認してください(廃止されると 404 になります)
- 無料枠のままでは `402 RESOURCE_EXHAUSTED` で止まりました。少額でもチャージが必要でした
- ログに原文・整形結果・APIキー・URLは残っていません(確認したのは
  `選択テキストを取得しました。文字数: 34` / `テキストを挿入しました…文字数: 28` / `書き換え率: 44.1%`)

**Gemini では設定画面の「Model」が使われません。** `GeminiFormatter` は `_settings.Model` を
読まず、モデル名は `Endpoint` の URL の中(`.../models/<モデル名>:generateContent`)で決まります。
Model 欄だけ埋めても `TODO-model` のまま呼びに行って失敗します。
設定画面の欄名も「モデル(控えのみ。送信には使われません)」に直し、エンドポイントへ埋める
ことを下に注記しました(欄を無くすと、どのモデルを使っているかの控えが残らなくなるため)。
